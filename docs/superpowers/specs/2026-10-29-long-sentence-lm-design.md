# 長句選字加強（小型語言模型）— 設計

日期：2026-10-29。第 3 階段，接在 `2026-10-29-adjacent-valid-sentence-design.md` 之後；使用者的決定標「使用者」，Claude 的決定標「我的決定」，留給實作的標「（建造者決定）」。

## 目的與原因

- 使用者的觀察：短句選字很準，句子一拉長就把對的選成錯的；打錯字救回讀音之後，字還是常選錯。
- 量測：
  - 現在的前後文模型（bigram）只看前一個詞。沒拿來訓練的維基、網頁各 1000 句，整句正確率 72.1%、69.6%。
  - 第 2 階段把詞對從 300 萬加到 950 萬，只多 1.45 個百分點（`docs/architecture/decisions.md` 2026-10-29），瓶頸不是詞對數。
  - 用現成的大語言模型（ckiplab gpt2-base，GPL，只做實驗）對前 10 名候選重新排序：整句 76.9% → 82.5%；打錯的句子 A–D 類多 4–13 個百分點（scratchpad 的 `rs_*`，2026-10-29）。前 10 名裡含正確答案的比例是 95.8%，這是重新排序的上限。

## 目標

- 加一個自己訓練的小型語言模型，能看整句。讓它在**每按一鍵時**就參與選字（使用者：打字時就要看到正確的字，不能停頓，速度要夠快）。
- 第 1 階段的整句分數（`run_score`，注音自動校正用來選讀音）也用到它，讓打錯救回後選字更準。
- 設定「**長句選字加強**」（使用者定的名稱），預設開啟（使用者 2026-10-30 在關卡依數字決定），放在「打字」頁、注音自動校正旁邊。
  - 說明文字（我的決定）：「看整句的意思選字，長句更準確。電腦較舊、打字覺得變慢時可以關閉。」
- 關閉時，行為和現在完全一樣。

## 成功標準（使用者，2026-10-29）

- 整句正確率：沒拿來訓練的維基 `train-00003`、CC-100 `train-00007` 各 1000 句，平均提高 **≥ 3 個百分點**。
- 長句：15 個字以上的句子，整句正確率提高 **≥ 5 個百分點**（我的提議）。關卡結果 +3.35，使用者 2026-10-30 接受。
- 注音自動校正的 D、E 類（`tools/autocorrect_eval.py` 自然句子那組）不低於 3.0.2 的數字。
- 怎麼量（我的決定）：
  - 用 `tools/evaluate.py` 的預設算法（讀音直接轉換、不經過鍵盤）的「整句全對」。兩份語料各算提升，再取平均。`--typed` 的數字也一起報告。
  - 長句另外取一組：同樣兩個評估檔，取 15–40 字的連續漢字片段各 1000 句。原本的取樣上限是 20 字，15 字以上的句數太少，雜訊太大。
  - 兩組基準都用現在的 `data/bigram.bin` 重新量（關閉語言模型），不直接引用 72.1% / 69.6%。

## 絕對不能發生

- 中英混打被破壞：
  - `autocorrect_eval.py` 的 English changed = 0；Chinese changed ≤ 1%（兩組）。
  - `tune_english.py` 全對；`code_memory_eval.py` 240/240。
  - 語言模型只在中文片段裡、同一組讀音的候選之間挑字（以及第 1 階段的讀音比較），不參與「這段是英文還是注音」的判斷。
- 使用者教的東西被蓋掉（使用者 2026-10-29 同意以下分法）：
  - **語言模型一律不能改**：這次選過的字（overrides，現在就是鎖定的）、個人詞庫的詞、學過的多字詞。例如學過「介面」的人不會被改成「界面」。要另外做一層保護，比照第 1 階段 `_makes_user_word` 的範圍。
  - **只是加分，可以比**：只選過的單字。這類紀錄照現在的方式只拿部分優勢（`SINGLE_EDGE`、`STRONG_PICKS`），語言模型可以和它比，免得「線＋在」打贏「現在」。
  - 自動學到的詞（`_learn_broken_words`、`_learn_tone_variant_words` 學的）也是學過的多字詞，同樣不能改。
- 打字變慢。以公司配的文書筆電為準（使用者）。上限是我的決定：
  - 每鍵在 C++ 引擎多花的時間，在開發機（這台）上 ≤ 2 ms（文書筆電約 ≤ 5 ms）。量的是 p95，不是平均。
  - 不允許因為模型讓某一鍵卡住超過 30 ms。
- 檔案和記憶體：
  - 安裝檔多 ≤ 15 MB（現在 14 MB）。
  - 引擎記憶體多 ≤ 50 MB；啟動時間多 ≤ 0.5 秒。
  - 模型檔 < 50 MB（GitHub 單檔上限 100 MB，超過 50 MB 推送會警告）。
- 兩個引擎結果不同：`tools/compare.py` 必須 "same"，包括設定開關兩種情況。
- 授權：模型自己訓練，不使用 GPL 的權重。語料沿用 README 已經標示的維基（CC BY-SA 3.0）與 CC-100，README 的來源說明補上「語言模型」。

## 已定的做法

- **影響範圍**（我的決定）：
  - 只影響自動選字（`convert` 的結果），以及注音自動校正選讀音（`run_score`）。
  - `repick` 不能把語言模型選的字換回去：同音字偏好照樣作用，但結果要和語言模型的判斷一致。
  - 按 ↓ 的候選清單順序、Tab 補字、替換列維持現在的樣子，保持使用者的習慣。替換列的預覽本來就跟著轉換結果走。
- **看多遠**（我的決定）：只看同一段連續的中文，和現在的 `convert` 一樣。
  - 不跨過中間的英文，不接續上一次送出的內容。
  - 訓練資料因此不需要英文佔位符號。
  - 之後若要跨英文或接續送出的內容，是另一件事。

- **訓練**：用 RTX 4090，語料是 `C:\Users\kenny\Data\corpus`。
  - 訓練用維基 `train-00000..00002`、CC-100 `train-00000..00006`。
  - 維基 `train-00003`、CC-100 `train-00007` 只當評估，和第 2 階段相同。
- **兩個引擎完全一致**：推論用整數或定點數（例如 int8 權重、int32 累加、查表做非線性），Python 和 C++ 各寫一份，同樣的運算順序。分數差極小的情況很多（重新評分實驗裡 11% 的錯誤分數差 ≤ 0.1），浮點數的差異就會讓兩邊選得不一樣。
- **新的資料檔**（例如 `data/lm.bin`）：
  - 由訓練與量化工具產生，不手改（`data/` 由 guard_paths 保護）。
  - 這是新的檔案種類，推送前 push_audit 會擋，例外由使用者加到 `.claude/push-audit-allow.txt`。
  - 安裝檔要帶上它。
- **分段做，每段有關卡**：
  1. 訓練幾種大小的模型，只做 Python 版。量正確率、長句、打錯救回、英文安全，以及一個能估算 C++ 速度的指標（例如每字的運算量，或先寫一個簡單的 C++ 推論量時間）。
  2. **關卡**：把數字給使用者，附上建議（要不要繼續；預設開或關）。達不到成功標準、或速度上限內做不到，就停下。
  3. 兩個引擎的整數推論、設定開關（四處預設值一致）、設定頁、安裝檔、實機測試、文件。
  4. 完整檢查、審查、提交、推上 `develop`、Pre-release 3.0.3（第 2 階段沒發版）。
- 預設值的四處要一致：`engine/config.py`、`cpp/engine/config.cpp`、`installer/src/Settings.cs`（預設與備份）、`settings/ui/bridge.js`。設定頁文字要一起改 `docs/settings-ui-kit-text.md`。

## 關卡結果（2026-10-30）

- 試了 S、M、L、XL 四種大小（逐字 GRU，詞嵌入與輸出共用一張表），在選字的前 10 名（n-best，每個狀態留 5 條路徑）加上 λ × 模型分數。beam 裡每條路徑都帶模型狀態的做法較差，也慢很多，不採用。
- 採用 **XL**：詞嵌入 384、GRU 768 × 2 層，字表 12,263 字，約 11.2M 個參數。int8 檔 11.6 MB，λ 0.5。開發集困惑度 39.3（L 是 51.8）。
- 整句正確率（int8）：
  - 一般 6–20 字：維基 72.1 → 76.7%、網頁 69.6 → 72.2%，平均 **+3.6**（通過）。
  - 長句 15–40 字：維基 56.5 → 60.3%、網頁 60.3 → 63.3%，平均 **+3.35**（未達 +5，使用者接受）。
  - float 是 +3.85 / +3.6，int8 只損失約 0.25 個百分點。
- 速度（估算）：C++ AVX2 每步 143µs。逐字估算每音節中位數 0.75 ms、p95 1.64 ms、最大 3.13 ms（開發機）。實作後要在 C++ 引擎實測。
- 注音自動校正：L 讓 D 類大幅變好（隨機 34.7 → 44.9%），但 Chinese changed 超過 1%，`SWAP_GAIN` 等門檻要重新調（3B）。XL 的數字待補。
- 工具在 `tools/lm/`（`prepare`、`train`、`quantize`、`intlm`、`decode`、`evaluate_lm`、`keysteps`、`autocorrect_lm`、`bench/`）。

## 留給建造者

- **模型種類與大小**：以「每按一鍵只算新增的部分」為前提，例如逐字的小型 RNN／GRU／LSTM，或小型 transformer 加快取。
- **字表**：常用字加未知字的處理。
- **怎麼接進選字**：
  - 例如在 beam search 裡把語言模型分數加到每條路徑（每條路徑帶著模型狀態），或對 beam 的前 N 名重新排序並快取前綴狀態。
  - 權重（λ）用沒拿來訓練的資料調。
  - 每按一鍵時，前面的文字通常沒變，計算要能重用。
- **Python 版的速度**：參考引擎目前沒有 numpy 等相依套件。可以只為了測試加入，但不能讓完整檢查（現在約 5 分鐘）慢到無法使用；必要時 `compare.py` 用較小的案例數跑開啟模型的那組設定（要附理由）。
- **評估工具**：例如 `tools/evaluate.py` 加長句的分組統計、`--lm` 選項，延遲量測比照 `tools/key_latency.py`。C++ 的每鍵延遲也要能量到 p95。
