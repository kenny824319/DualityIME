# 句尾順序打反的數字音節用語言模型判斷 — 設計

日期：2026-11-04。使用者的決定標「使用者」，Claude 的決定標「我的決定」，留給實作的標「（建造者決定）」。

## 目的與原因

- 使用者回報（2026-11-03）：打「我們走」接著 `817`（ㄅㄚ˙ 的按鍵順序打反，應該是 `187`），結果還是數字，沒變成「吧」。
- 現在的規則（`engine/composer.py` `_check_corrections`，`cpp/engine/composer.cpp` `check_corrections`）：注音自動校正把順序打反的數字音節（token `corrected == "order"`）在兩種情況下才保留成中文——單獨打（前後都不是中文或英文），或和旁邊的音節組成比分開好 `ORDER_DIGITS_GAIN` 的字典詞（「好817」→ 好吧）；其他都變回數字，避免把真的數字改掉。量測（2026-11-03）：20 個常見句尾接 817，只有 1 個變成吧。
- 使用者要的分辨（2026-11-04）：「房間號碼是817」要維持數字，「我們走817 ok」要變成吧。前後文可以分辨，長句選字加強的語言模型做得到：在前面的中文之後，下一個字是某個音節的字的**絕對機率**（整個字表的 softmax，不是只在同音字間比），兩群差很多。

## 量測（2026-11-04，scratchpad 的 `ba_syllables*.py`、`ba_thresholds.py`）

- 語料：沒拿去訓練的網頁 `tools/lm/common.EVAL["web"]`。
  - 該變中文的：每個音節的字出現在一段中文的最後一個字（後面是結尾、標點、空白或英文字母），取前面的中文（最多 20 字）當前文，每音節最多 300 句。
  - 該維持數字的：一段中文後面接 1–6 位數字、數字後面是結尾、標點、空白或英文字母，取前面的中文當前文，6000 句。模型看不到數字，所以每個音節都用同一批。
- 指標：P(音節 | 前文) = 該音節所有候選字（`Scorer.candidates(音節)`）的絕對機率加總。
- 只看「吧」（`ba_corpus.py`，各 2000 句）：吧的中位數 0.021、數字的中位數 0.00005；門檻 0.02 時吧 51% 改對、數字 0.15% 被改錯。
- 全部音節共用 0.02 時，常用字的音節數字被改錯太多（帶 9.1%、大 6.4%、達 5.3%、白 5.0%、百 4.9%、站 3.1%、半 3.1%、但 1.4%），所以每個音節各自調門檻（使用者）：從 0.02 往上調，直到數字被改錯 ≤ 0.25%（和吧在 0.02 時相當）。分成兩半驗證（3000 句決定門檻、3000 句驗證）時，驗證那一半是 0–0.6%。

## 決定

### 什麼時候用模型判斷（使用者，我的決定補細節）

全部成立才用：
1. 注音自動校正開啟，而且長句選字加強開啟、模型有載入（`lm.shared()` 不是 None）。任一個關閉：完全照現在的規則（使用者）。
2. token 是順序打反的數字音節（`corrected == "order"`），而且現在的規則會把它變回數字：不是單獨打、也組不成夠好的字典詞，使用者也沒有選兩次記成數字（`picked(t) in ("", AS_ENGLISH)` 時照舊是數字）。
3. 它是一段中文（`_zh_runs` 的一個 run）的**最後一個音節**，而且前面至少有一個中文音節（`k == len(run) - 1` 且 `k > 0`）。後面接什麼都可以：結尾、標點、空白、英文（使用者：「我們走817 ok」要變吧）。後面還接中文（「817個」）不在範圍內，維持數字。前面是英文或數字（`you are 817`）時它是 run 的第一個，不在範圍內，維持數字。
   - **後面緊接著還沒打完的音節（`partial` token）算「後面還接中文」，維持數字**（使用者，2026-11-04）。`_zh_runs` 遇到 partial 會把 run 切斷，817 看起來會是 run 的最後一個，所以要另外檢查 tokens 裡緊接在它後面的那個不是 `zh` 也不是 `partial`。理由：打「我們走817」再按下「個」的第一個鍵時，不要先變「我們走吧ㄍ」、打完又跳回「我們走817個」。代價：打完「我們走817」停下來時是「吧」，再接著打中文的那一刻會跳回 817。
   - （注意）`817 o` 這種接著英文字母、第一個字母還能讀成注音的情況，也會暫時是 partial；接著打完英文就回到「吧」。可以接受，建造者不用特別處理。
4. P(音節 | 前文) ≥ 該音節的門檻：成立就保留成中文（不加進 `numbers`），否則照舊變回數字。

### 前文怎麼來（我的決定）

- 判斷放在 `_check_corrections` 第一個迴圈（現在決定 817 留中文或變數字的地方），前文用**這時的讀音**，也就是其他自動校正（漏打聲調、按到隔壁鍵、換音節）還沒做之前的讀音（我的決定，2026-11-04）。理由：改用校正後的讀音要把判斷挪到第二個迴圈之後、再把 token 轉回數字，兩個引擎的結構都要大改；817 前面剛好也有打錯的情況少。之後真的遇到再改。
- `_check_corrections` 在選字之前，只有讀音。前文 = 這個 run 前 k 個音節照引擎原本的選字（`convert(readings[:k], lexicon, user, {}, bigram)`，不帶模型、不帶這次選過的字）寫成的字，從 run 的開頭算（和 `Scorer` 一樣，`<s>` 後接這些字）。寫出來的字數不等於 k（例如某個音節沒有字）時不判斷，維持數字。
- （建造者決定）是否改用帶模型的 `convert` 結果；要的話量 `tools/key_latency.py` 的差別再決定。

### 機率怎麼算，兩個引擎要逐位元相同（我的決定）

- 用模型現有的整數運算：在前文的狀態下，對**整個字表**算 Q10 的對數機率（`CharLM.scores(state, 全部 id)`，C++ 對應的函式），再用模型的 exp 表（Q16）把該音節候選字的值加總成整數 `p_q16`，和門檻的 Q16 整數（`round(門檻 × 65536)`）比較。不經過浮點的 exp/log，兩個引擎才會在門檻邊界做一樣的判斷。
- 候選字和 `Scorer.candidates(音節)` 相同（字典裡寫成這個音節的字；模型不認得的字 id 0 不算）。
- 快取：同一個（前文, 音節）的結果保留到前文改變（建造者決定，可以和 `Scorer` 的狀態快取共用上限 `LM_STATES_KEPT`；key 要和 `score_cache`「只在同音字間正規化」的分數分開）。
- C++ 端整個字表的加總用 int64；門檻以 Q16 整數存（我的決定）。

## 目標

- 句尾的順序打反數字音節，前文讓它很像中文時自動改對：「我們走817」→ 我們走吧、「我們走817 ok」→ 我們走吧 ok。
- 真的數字很少被改：「房間號碼是817」「跑了817 km」維持數字。
- 改錯的時候，↓ 清單照舊有原本的數字可以選回；選回兩次就記住（現有的校正記憶）。

## 非目標

- 看後面的字（模型只看左邊）：「跑了817 km」會不會變吧只靠「跑了」決定（實測 P(吧|跑了)=0.004，低於 0.0246，維持數字）。
- 單一個字的前文（「他817」「對817」）：模型判斷不出來（P 很低），維持數字。
- 長句選字加強關閉、或注音自動校正關閉時的行為：不變。
- 句中（後面還接中文）的數字。

## 反目標（做了也算失敗）

- 使用者打的電話、價錢、編號常被改成中文。驗收用數字被改錯的比例（上面的表）把關。
- 每鍵變慢到感覺得出來。

## 驗收

- 單元測試（`tests/test_engine.py`，長句選字加強與注音自動校正都開）：
  - 「我們走817」→ 我們走吧；「我們走817 ok」→ 我們走吧 ok；「算了817」→ 算了吧（實測 P 0.23）
  - 「房間號碼是817」→ 數字；「電話是824」→ 數字；「跑了817 km」→ 數字；「817個」（接中文）→ 數字
  - 「我們走817」接著按下一個音節的第一個鍵（partial）→ 數字，不先變吧
  - 長句選字加強關閉、注音自動校正關閉時「我們走817」→ 數字
  - 兩個引擎的門檻表相同
- `tools/compare.py`：加上述案例的按鍵，兩個引擎 same。
- e2e：`cpp/tools/autocorrect_cases.txt` 加「我們走817」「房間號碼是817」各一行（`-Config cpp\tools\autocorrect_config.json`，長句選字加強在預設是開的；建造者確認那份設定沒有關掉它）。
- `tools/autocorrect_eval.py`：英文被改成中文維持 0、打對的中文被改 ≤ 1%（目前 0.62% / 0.00%）。
- 速度：`tools/key_latency_cpp.py`（和 decisions.md 長句選字加強那條同樣的量法），有順序打反的數字音節在句尾時每鍵增加的時間；目標每鍵 p95 多不超過 2 ms（我的決定，建造者量了報告，超過再和使用者討論）。
