# 設計決策與理由

只記錄從程式碼看不出來的「為什麼」。新增決策時寫：決定、理由、日期。

## 引擎與打字

- **Python 引擎是標準答案，C++ 引擎照著做**
  - 理由：Python 好寫、好測、好調參數；C++ 才跑得進 TSF、夠快。`tools/compare.py` 把同一批按鍵在 5 組設定下餵給兩邊，逐鍵比對輸出、`user.json` 與 `keys.json`，任何分歧都會被抓到。

- **只支援標準（大千）鍵盤**
  - 理由：使用者幾乎都用標準排列；多一種排列，引擎、記憶（`keys.json` 要分段）、設定與測試都要多維護一份。`keys.json` 只有 `standard` 段。

- **注音自動校正預設關閉，關著時行為與沒有這個功能一樣（只有代碼記憶例外）**
  - 理由：這個輸入法的特色是不用切換就能中英混打，校正本質上是跟「拼不成注音就是英文」搶按鍵；開了就要接受偶爾改錯，所以做成開關，設定說明附提醒。
  - 驗收：英文誤判為 0，打對的中文被改掉 ≤ 1%（`tools/autocorrect_eval.py`）。

- **注音自動校正看整句：漏打聲調、按到隔壁鍵拼成另一個音（2026-10-29）**
  - 決定：
    - 按到隔壁鍵、剛好拼成另一個音（D）時，用前後各 3 個音節的整句分數（字典加前後文模型）比較照打的讀音和能組成詞的隔壁鍵讀音。打的音不成詞，要好 3.5 才換；成內建字典的詞，要好 3.0 才換（「你老嗎」→「你好嘛」；調出來的，成詞並沒有比較常是對的）。成個人詞庫或學過的詞（任何長度）時一律不換。
    - 漏打聲調（E，`5k1u0 ` → 這邊）：沒有聲調的一段注音，後面緊接著一個以聲母或介音開頭的音節時，當成一個音節，聲調用整句分數選，能組成使用者的詞的聲調優先（`5km3` 有「哲宇」時是哲宇）。緊接在英文後面（沒有空白）時不算（`su5k1u0 ` 維持「su5k邊」）。選過的聲調不會被之後打的字改掉。
    - 標點鍵開頭、順序打反的音節（`;e ` → 剛），只在標點鍵後面那幾個鍵自己拼不成音時才重排，所以 `,u3` 仍是「,以」；其中有數字時只在中文後面重排（`su3.2 ` 是「你都」，`no.2 `、`you are 3.2 ` 照舊）。和其他校正一樣，↓ 清單最後是原本的按鍵，選回 2 次就記住。
  - 理由：使用者回報手機會把「5k邊」「剛;e」改對。原本 D 只要打的音成詞就完全不換，不成詞時也只看左右 2–3 字的字典分數。
  - 整句分數不看使用者的學習紀錄，同樣的音節分數永遠一樣，可以跨按鍵快取；不快取時每鍵 p95 是 40 ms。
  - 漏打聲調的音節後面不能接只有韻母的音節。不然 A 類（按到隔壁鍵拼不成音）的 `2u.4` 會被讀成 `2u` + `.4`（ㄡˋ），A 從 71.7% 掉到 69%。
  - 量測（`tools/autocorrect_eval.py`，新增 repo 文件裡的 600 句自然句子；改前 → 改後）：
    - 自然句子：A 71.7% → 71.1%、B 89.4% → 92.8%、C 72.5% → 72.7%、D 14.1% → 39.6%、E 0% → 62.7%
    - 打對被改：隨機詞組 0.88% → 0.75%、自然句子 0.17% → 0.17%；英文誤判 0 → 0
    - 門檻是在這些限制下掃出來的：不成詞的門檻 3.0 時，隨機詞組被改 1.12–1.25%，超過 1%。
    - 審查修正之後的最終結果（自然句子取自更新後的文件，句子組成不同，不能和上面逐項比）：自然句子 A 71.2%、B 91.3%、C 73.3%、D 47.8%、E 63.7%；隨機詞組 A 75.0%、B 90.1%、C 80.8%、D 34.0%、E 64.3%；打對被改 0.75% / 0.17%；英文誤判 0。
  - 延遲（`tools/key_latency.py`，自動校正開啟，最長 30 句，暖身句不計時）：Python 每鍵 p95 5.0 → 7.2–7.4 ms、最慢 11 → 14–22 ms。C++（`sz_trace.exe`，含輸出）每鍵平均 0.69 ms，關閉時 0.39 ms。

- **單字選過一兩次，句子裡只多一點點分數（2026-10-30）**
  - 決定：句子裡單獨一個字的位置，選過的字只加 log10(1 + 選過幾次)（1 次 0.3、10 次 1.0），不是學過的詞那種 3 分以上，個人詞庫的字才用完整加分；選字時那個位置的優勢（`single_scores` 的 edge）也只留給個人詞庫的字。字要塞進詞裡（謝謝妳、她說）要「確定的習慣」：個人詞庫，或選滿 5 次（原本 3 次）而且至少是那個音最常用字的 2 倍（妳 5 次、你 4 次不算，免得多選一次就到處變妳），那時才用完整加分。只打一個音、沒有別的字時照舊用完整加分（選過「輸」，只打 ㄕㄨ 就是「輸」；「讀 python 輸」的 ㄕㄨ 算在句子裡）。你學過的詞被你改掉時，改成的寫法記半次（和湊對學詞一樣，選兩次、同一句只算一次）。
  - 原因（使用者回報「選字變笨了」：畫出→話出、因為→音位、注→住）：選過一次的單字直接加 3 分，前後文壓不過它，之後所有單獨成字的那個音都變成它；選滿 3 次的字還會塞進所有同音的詞裡（國際→國記、計劃→記畫、旗艦→歧見）。
  - 量測（使用者的學習紀錄副本，維基／網頁 6–20 字、沒拿去訓練的句子各 300 句，長句選字加強關閉，整句全對）：沒有學習紀錄 73.3% / 58.3%；原本 48.0% / 50.0%；改後 70.0% / 58.3%（15–40 字：64.7 / 58.7 → 改後 63.3 / 57.3）。長句選字加強開啟時（各 200 句）：79.0 / 69.5 → 77.0 / 70.0。拆開量（維基 400 句）：只用詞的紀錄 76.2%，和沒有學習紀錄相同；只用 186 筆單字紀錄 50.5%，損失全在單字。
  - 句子裡單獨一個字也照「確定的習慣」用完整加分（審查建議，讓同一個字在詞裡、句子裡一致）量過不採用：改後掉到 66.7% / 56.3%。這位使用者「確定的習慣」多半是同一個地方反覆選出來的（「載」23 次為了下載、「繪」36 次為了重繪），會搶走句子裡所有單獨的「在」「會」。要在句子裡也照自己的寫，加進個人詞庫。
  - 代價：選過一兩次的單字，在句子裡不再一定出現；同一個地方要記住，靠湊對學詞（選 2 次）或個人詞庫。

- **長句選字加強：自己訓練的小型語言模型（第 3 階段，2026-10-30）**
  - 決定：逐字 GRU（XL：詞嵌入 384、768 × 2 層，字表 12,263 字，int8 的 `data/lm.bin` 11.6 MB），用 `tools/lm/` 在 RTX 4090 上用 wikipedia-zhtw 與 CC-100 訓練，不用任何 GPL 的權重。只用整數運算，兩個引擎逐位元相同（`tools/lm/check_cpp.py`）。預設開啟。
  - 用法：選字照原本的搜尋，取前 10 個不同的句子（每個狀態留 5 條路徑），分數加上 0.5 × 模型的 log10 機率，比原本的選擇嚴格好才換。beam 裡每條路徑都帶模型狀態的做法較差也較慢，不採用。
  - 不會被模型換掉的：這次選過的字（和圍著它的詞）、個人詞庫的詞、學過的多字詞；只選過的單字是加分，可以和模型比。只有一個音節時不用模型（它只看得到句首，使用者的「妳」會輸）。
  - 注音自動校正判斷要不要換讀音時不用模型（使用者決定）：第一版讓它也用，每鍵 p95 多 12.7 ms，86% 的模型計算花在這裡，換來 D 類 +0.5、E 類持平，而且為了不改打對的字要把門檻調高，「今篇→今天」反而不換。
  - 量測（`tools/lm/evaluate_lm.py`，沒拿來訓練的檔案）：整句正確率一般 6–20 字平均 +3.6 個百分點（維基 72.1 → 76.7%、網頁 69.6 → 72.2%），長句 15–40 字平均 +3.35（56.5 → 60.3%、60.3 → 63.3%；目標 +5，使用者接受）。注音自動校正的數字和 3.0.2 相同。
  - 速度（`tools/key_latency_cpp.py`，i9-13900K）：AVX2 每鍵 p95 多約 1.5 ms、模型造成的最慢一鍵約 22 ms；沒有 AVX2 的 CPU p95 多 4.5 ms、最慢約 70 ms。記憶體多 18 MB，啟動多 0.12 秒；設定關閉時不讀模型檔。最大的開銷原本不在模型，而在每條路徑的 `repick` 重查同音字偏好（同一次選字裡記住後少 90%）。

- **前後文模型不加大（第 2 階段停止，2026-10-29）**
  - 決定：`data/bigram.bin` 維持 300 萬組詞，不換；直接做小型語言模型（第 3 階段）。
  - 量測（`tools/evaluate.py`，沒拿來訓練的維基 `train-00003`、CC-100 `train-00007` 各 1000 句；用 10 個語料檔整個重建，8.5 億個詞）：整句正確率維基 72.1% / 網頁 69.6%（現在）→ 300 萬組 72.3 / 69.7、500 萬組 72.7 / 70.7、950 萬組 72.4 / 72.2。平均最多多 1.45 個百分點，沒到使用者訂的 2 個百分點；950 萬組的檔案是 95 MB（GitHub 單檔上限 100 MB）、安裝檔多約 22 MB。
  - 理由：多收詞對的效果很快就不再增加，瓶頸是 bigram 只看前一個詞。同一類句子用現成語言模型重新排序，整句多 5.6 個百分點（2026-10-29 的實驗）。
  - 重建的三個都讓中英混打 `18 ` 從「八」變「吧」：前後文統計按字數、不分讀音，網頁裡大量的輕聲語助詞「吧」（`187`）也算進一聲的「吧」（字典把「吧」列在 ㄅㄚ 和 ㄅㄚ˙，分數相同）。語料越多越明顯。

- **「前一句是英文時 1–2 字母字的折扣」不改**
  - 理由：想讓 `look gpt4` 不變成「look gp赤」，量過真實例子：修好 12 個代碼，卻弄壞 64 個通順的中英夾雜（up還是、no謝謝）。兩者按鍵上分辨不出來，改用代碼記憶由使用者教。

- **含數字的代碼不直接用「選一次就記成英文」**
  - 理由：替換列每個字都列出按鍵，`ji3`（我）不小心選一次就永遠是英文，而且救不回來。所以走代碼記憶：選 2 次、會淡掉、↓ 可改回。

- **字典裡聲調不同的詞，選一個字改出來就記成整個詞（2026-10-29）**
  - 決定：選字和左右的字合起來，是字典裡只差聲調的詞（字典的「下載」是 ㄒㄧㄚˋ ㄗㄞˇ，打教育部讀音 ㄗㄞˋ 出「下在」），而且每個字都有打的讀音（「載」也唸 ㄗㄞˋ），就記成打的注音底下的詞。只差輕聲也算，只看內建字典。
  - 理由：原本只記住單字「載」，但「在」是 ㄗㄞˋ 最常用的字，選再多次也帶不進詞裡（同音字偏好要排第一，而且使用者沒有也常選「在」，否則「現在」會變「現載」）。改 30 次仍然是「下在」。
  - 代價（使用者同意）：一次修正分不出是字典的聲調不同，還是自己打錯聲調。打成 `ㄋㄚˇ ㄒㄧㄝ`，把「哪些」改成「那些」，之後也會學起來，要再改回一次。內建字典裡符合條件的有 3,972 組，兩邊都是常用詞的有 223 組；不加「每個字都有打的讀音」這個條件的話是 104,523 組。
  - 字典裡沒有的詞：見下一條（2026-10-30，選 2 次才學）。

- **注音自動校正把「只差一個字的聲調就是字典的詞」當成那個詞來比（2026-10-30）**
  - 決定：打的音和旁邊的音只差一個字的聲調就是字典的詞（教育部讀音對字典：ㄆㄧ ㄆㄟˋ 對 ㄆㄧˇ ㄆㄟˋ「匹配」、ㄕㄠˋ ㄕㄨˋ 對 ㄕㄠˇ ㄕㄨˋ「少數」），比要不要換音時，打的讀音的分數以那個詞的讀音來算；聲調差在別的字上（匹配的「匹」），被換的那個字就完全不換。先打出「批配」，選一次「匹」就學成「匹配」（下載那套）。
  - 原因（使用者回報）：照教育部讀音打「匹配」，`o`（ㄟ）旁邊是 `0`（ㄢ），換成 ㄆㄢˋ 剛好是「批判」、整句又更通順，所以被換掉；第二個字的清單變成 ㄆㄢˋ 的字，「配」排在第 23 個，先把「批」改成「匹」也救不回來。
  - 只差一個字：兩個字聲調都不同的不算（「部分」打錯成 ㄅㄧˋ ㄈㄣˋ，剛好是「比分」ㄅㄧˇ ㄈㄣ 換了兩個聲調，那是打錯，照樣救回）。
  - 量測：第一版只擋「聲調差在別的字上」，審查實測 5493 組相鄰鍵打錯少救 5 組（部分→必份等）、字典裡只差聲調的 1664 組兩字詞仍有 5 組被換（少數→上述、看起→開啟）；改成上面的做法後這幾個例子都對（tests：`test_a_word_read_with_other_tones_is_not_swapped`、`test_a_tone_of_the_ministry_is_scored_as_the_word`、`test_a_slip_spelling_another_tone_of_a_word_is_still_put_right`），整體數字見 `tools/autocorrect_eval.py` 的結果（commit 訊息）。
  - 同時（使用者：保留選字的權力）：被換過的字按 ↓，原本打的音最常用的 3 個字排在第 2 到第 4 個，其餘在後面（原本全部排在換過的讀音的字之後，「現」在第 31 個；全部插到第 2 個又會把換過的讀音的其他字和詞擠到很後面）。

- **字典裡沒有的兩字詞，同樣的地方選 2 次就學成詞（2026-10-30）**
  - 決定：選的字和旁邊一個單獨的字湊成兩個字、字典裡沒有這個詞（在「重」後面選「繪」），每次送出記「重繪」半次，第二次滿一次就是學過的詞。每次選字只湊一對：左邊是單獨的字就湊左邊，否則湊右邊（使用者 2026-10-30；左右都湊的話「重繪了」會學到「繪了」，「我會了」就變「我繪了」）；只算真的換了字的選擇；旁邊的字屬於一個詞（自訂 + 蟲）、選的字在詞裡（你好 → 你郝）、兩個都選了（交給相鄰選字學詞）、字典裡已有的詞（交給下載那套），都不湊對。同一句送出只算一次；之後改回去照原規則忘掉。
  - 原因（使用者回報）：「繪」選了 36 次還是「重會」。單字加分照次數取對數成長，常用字「會」只要選過 2 次，加分就只差 1.26，追不上它在詞庫裡的分數；單字的紀錄也不知道是在哪個字旁邊選的。
  - 為什麼不用新檔案：學習紀錄本來就用小數計次，未滿 1 次不加分、不進候選，所以半次放在 `user.json` 就好，匯出、匯入、備份、全部清除、送出後復原都直接適用。裝回 3.0.3 以前的版本時，它在下次存檔清掉半次之前，會把半次當成學過的詞（只影響注音自動校正不換那兩個音、長句選字加強不換那兩個字）。半次只保留到淡化（20 天）為止。
  - 代價：同樣的地方選 2 次，名字和打錯的字也會學起來（以前只選 1 次就不會）。

- **單一個字母不記成英文（2026-10-27）**
  - 理由：一個字母（`t`、`a`）從替換列選回原本的按鍵，若記成英文，從此打不出那個注音（`t` 是「吃」的ㄔ）。所以只改那一次；檔案裡已經有的單一字母，讀取時忽略、下次存檔時拿掉。

- **引擎不以系統管理員權限服務（2026-10-31）**
  - 原因（使用者回報）：在其他程式都打不出中文。引擎是被以系統管理員身分執行的程式（裡面的輸入法在沒有引擎時會啟動它）或系統管理員視窗裡的腳本叫起來的，跟著有了系統管理員權限；它建立的通道擁有者是 Administrators，一般程式被拒絕。
  - 決定：引擎一啟動若有系統管理員權限，就以桌面 explorer 為父程序、用 explorer 的權限重開一份自己，自己結束（只在 explorer 不是系統管理員權限、而且是同一個帳號時；SYSTEM 或別的帳號的程式等的是自己帳號的通道）。重開不了就自己服務，而通道明確允許使用者的 SID，一般程式照樣連得上。測試腳本用 `--keep-elevated` 留在系統管理員權限（測試視窗也是，並且用 PID 追蹤）。

## 記憶檔

- **校正記憶與代碼記憶存在獨立的 `keys.json`，不放 `user.json`**
  - 理由：引擎存 `user.json` 時會丟掉不認得的欄位，分開放，新的記憶就不會被別的版本弄丟；分開也讓「功能關著不碰」容易做到。
  - 選擇分三種：`""` 照打（不校正）、讀法（照那個音節）、`"en"` 當英文（代碼）。`""` 和 `"en"` 分開，否則在「好」上選回「老」兩次，`xl3` 會被當成英文。
  - 選 2 次、比其他選擇都多才生效；每 20 天減半；只有使用者選的時候算「用到」，所以不再需要的記錄會自己淡掉。設定視窗不加任何按鈕（使用者決定），用「全部清除」清。

- **Email 獨立記錄、不會淡掉；不記網址（2026-10-27）**
  - 理由：Email 要一字不差，打過一次就該記住，久沒用也不該消失；混在英文單字裡會跟著半衰期減半、被常用字擠掉。所以 `user.json` 有自己的 `emails` 與 `used.emails`，超過 2000 筆才丟掉最久沒用的。網址多半只打一次、又長又雜，記了只會讓 Tab 補完出現不要的東西：照樣當英文輸出，只是不記。

- **「全部清除」清掉所有打字記憶，Email 另外勾選（2026-10-27）**
  - 理由：使用者按「全部清除」是想讓輸入法回到沒學過的樣子（例如某個鍵被記成英文），只清一部分等於沒清。設定與個人詞庫是使用者自己輸入的，不算記憶，保留。Email 重新累積的代價高，預設留著。
  - 由引擎清（設定工具把 `forget_words`／`forget_emails` 計數器加 1，引擎看到就清）：引擎開著時會把記憶寫回檔案，設定工具直接刪檔會被蓋回去。

## 名稱、安裝與更新

- **GUID 沿用 2.x 的那一組，只改名稱與檔案位置**
  - 理由：Windows 把它當成同一個輸入法換了名字：語言清單裡的項目、預設輸入法、每個帳號的啟用狀態都不用動，升級的人不用重新設定。

- **舊格式只在兩個地方轉換：`installer/src/Migrate.cs` 與引擎的一次性搬家**
  - 理由：相容程式散在各處，每個地方都要記得兩種格式。安裝檔（以及匯入備份檔）用 `Migrate.cs` 把舊資料轉成目前的格式；這台電腦的其他帳號，引擎在那個帳號啟動時，若 2.x 的資料夾裡有資料、而 `%APPDATA%\DualityIME` 裡還沒有 `user.json`、`config.json`、`keys.json`、`dictionary.json` 任何一個，就請 `settings.exe --migrate-user` 搬，搬好之後不再看。兩套引擎與設定網頁只認目前的格式。
  - 搬完、確認新檔案都寫好才刪舊資料夾，任何一步失敗就保留舊資料夾：資料不能兩邊都沒有。
  - 「搬過了」只有一條規則（安裝檔、`--migrate-user`、設定視窗、引擎共用）：新資料夾裡有上面四個檔案之一，而且沒有 `migrating` 這個檔案。不能只看資料夾在不在：符號鍵盤會在那裡寫 `keyboard.json`，搬到一半失敗也可能先建了資料夾（失敗時會把自己建的空資料夾刪掉，下次再搬）。搬移開始複製前先寫 `migrating`、舊檔刪完才拿掉：搬到一半被中斷（程式被關、當機）時下一次會接著搬，新資料夾裡已有的檔案留著、缺的補上。安裝檔、設定視窗與引擎可能同時搬，所以一次只讓一個搬（同一個資料夾一個鎖），暫存檔名也各自不同。
  - 引擎最多等 `--migrate-user` 60 秒（它自己可能要等安裝檔的搬移 30 秒）；沒有搬完時（60 秒後還在搬、搬移失敗、沒能啟動），這次執行期間引擎不寫 `user.json`、`keys.json`、`config.json`（學到的、切換的只留在記憶體），免得新寫的檔案被當成已經搬過、或蓋掉正在搬進來的資料，下次啟動再搬、再讀。搬移寫每個檔案時先完整寫進暫存檔再改名，中斷時不會留下寫一半的檔案。設定視窗打開時若 2.x 的資料還沒搬，先搬再讀設定，免得在引擎第一次啟動前改的設定擋住搬移。
  - 2.x 的 `config.json` 搬過來時，「全部清除」的計數（`forget_words`、`forget_emails`）改成 2.x `user.json` 記下已處理的數字（沒有或讀不到就是 0）：3.0 的「全部清除」會清掉所有打字記憶，2.x 計數若剛好領先，第一次改設定就會全部清掉。

- **安裝檔是單一檔案，從 GitHub Releases 下載；建置出來的檔案不放進 git**
  - 理由：使用者大多不熟 git，下載一個檔案雙擊就能裝最簡單。安裝檔裡帶著所有要安裝的東西（內嵌 `payload.zip`），在任何資料夾都能執行。`bin/`、`out/` 只是建置結果，安裝檔只由 `tools/release.ps1`（或 `installer\build.ps1 -Release`）產生、附在 Release 上。
  - 安裝檔沒有程式碼簽章（使用者決定），README 說明 SmartScreen 的「其他資訊 → 仍要執行」。

- **使用者層級的步驟在沒有提權的程序裡做**
  - 理由：標準使用者輸入管理員密碼提權後，`HKCU` 與 `%APPDATA%` 是管理員的。所以安裝檔以使用者身分執行，資料搬移、`HKCU`、鍵盤清單在自己的程序裡做，只有 `Program Files`、HKLM、DLL 註冊交給提權的 `install.ps1`。解除安裝同理（`user.ps1 -Uninstall` 先整理鍵盤清單，成功才讓提權的部分移除程式）。

- **第一次安裝加進鍵盤清單，但不設為預設輸入法（使用者決定，2026-10-27）**
  - 理由：裝了就搶走預設輸入法太霸道；想要的人在設定「一般」頁打開「設為預設輸入法」。之後的安裝與更新（含從 2.x 升級）不動鍵盤清單與預設輸入法，也不把使用者自己拿掉的項目加回去：是不是預設就是 Windows 當下的狀態。
  - 「設為預設輸入法」不會多出中文(香港)的鍵盤：輸入法同時登錄給中文(台灣)與中文(香港)，Windows 設預設輸入法時會把中文(香港)加進登入時載入的清單；放在中文(台灣)底下、使用者自己沒有中文(香港)時，設完就拿掉。

- **安裝與更新絕不取消註冊輸入法**
  - 理由：新舊版本共用同一組 GUID，取消註冊（`UnregisterProfile`）可能讓各帳號的語言清單掉了這個輸入法。直接重新註冊就會蓋過 CLSID 指向的位置；只有解除安裝才取消註冊。新版註冊成功後才移除舊版程式，失敗時恢復原本的版本。

- **安裝與更新絕不重新開機**
  - 理由：被占用的舊檔改名移開、新檔立刻放上，改名的舊檔排到下次開機刪除；什麼時候重新開機由使用者決定。

- **更新只看 GitHub Releases；版號比目前大才更新**
  - 理由：不需要 git、不需要登入（公開 API）。版號 X.Y.Z 逐欄用數字比（3.2.0 > 3.1.12），一樣或比較小就是最新，不降版。下載後比對 GitHub 給的檔案大小與 SHA-256，安裝檔先用 `--expect-version` 確認內容版本與檔名一致，裝好再讀 `version.txt` 確認；任何一步失敗都維持原本的版本（安裝前備份安裝資料夾，失敗就還原）。
  - 「關於」頁打開時不連網：當前版本一直顯示，正式版與 beta 版按「檢查更新」之後才查。

- **Beta 勾選只決定看哪一種 Release**
  - 理由：沒勾只看正式 Release，有勾連 Pre-release 一起看，沒有其他意義。檢查之後改了勾選，結果回到「還沒檢查」，免得照著另一種設定查到的結果更新。

- **版號與分支：`main` 是 X.Y.0，`develop` 從 X.Y.1 往上數**
  - 理由：測試者看版號就知道是正式版還是測試版。推 `develop` 時，只要有會打包進安裝檔的東西（`cpp/`、`installer/`、`settings/`、`data/`、`VERSION`）改變，就加一次版號並建立 Pre-release（一次推送只加 1）；發正式版是使用者的決定。
  - 發版腳本先提交版號再跑完整檢查，所以檢查記下的就是要推的內容；推送由 Claude 自己執行，讓 push 前的檢查照常運作；tag 由 GitHub 建立，本機不下 tag。
  - 正式版的版號提交只在 `main` 上，`develop` 若沒把它合回來，下一個測試版會照自己的 `VERSION` 編出比正式版還小的版號。所以 `develop` 的 prepare 在 `origin/main` 有 `develop` 沒有的提交時先停下來；`main` 發版完會印出把 `develop` 跟上 `main` 的指令（腳本自己不推送）。
